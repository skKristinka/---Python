# Документация проекта

## 1. Назначение

Учебный проект: понять HTTP «под капотом», спроектировать ООП-архитектуру и освоить многопоточность в GUI-приложении. Клиент и сервер реализованы на «голых» сокетах, GUI — на Tkinter.

## 2. Архитектура

Зависимости направлены только вниз:

```
gui  ->  client, server  ->  net, http  ->  interfaces
```

| Пакет | Классы и модули | Назначение |
|---|---|---|
| `src/interfaces.py` | `RequestHandler`, `Transport` (ABC) | Абстракции: обработчик запроса и транспорт байтов |
| `src/http` | `Url`, `Request`, `Response`, `Parser`, `Serializer`, `read_message`, `ParseError`, `HttpError` | Модели, разбор и сборка HTTP, чтение сообщения из сокета |
| `src/net` | `Socket`, `TcpClient`, `TcpServer` | Сокеты: контекстный менеджер, подключение, bind/listen/accept |
| `src/client` | `HttpClient` | GET/POST, таймаут, редиректы, https |
| `src/server` | `HttpServer`, `Router`, `LogEntry`, `handlers` | Сервер в потоках, маршруты, лог для GUI |
| `src/gui` | `App`, `ClientTab`, `ServerTab`, `SettingsTab`, `HeaderTable`, `LogTable`, `HighlightedText`, `StatusIndicator`, `RequestWorker`, `Settings`, `HistoryStore` | Интерфейс и его логика |

Интерфейсы (ABC): `Transport` реализует `Socket`, `RequestHandler` реализует `Router`. `HttpServer` зависит от абстракции `RequestHandler`, а не от конкретного роутера; `read_message` — от `Transport`, поэтому его проверяют на фейковом транспорте без сети.

Диаграммы классов: [ядро](docs/class_diagram.png), [GUI](docs/class_diagram_gui.png) (исходники — `.puml`).

## 3. Реализация HTTP

- **URL.** `Url.parse` разбирает `scheme://host[:port][/path][?query][#fragment]`; порт по умолчанию 80/443, диапазон порта 1–65535.
- **Разбор.** `Parser` проверяет стартовую строку, имена заголовков (токены RFC 7230), `Host` для HTTP/1.1, `Content-Length` (только цифры 0–9) и `Transfer-Encoding: chunked`. Заголовки ограничены 8 КБ, тело — 10 МБ.
- **Сборка.** `Serializer` сам ставит `Content-Length` и `Date` в ответах и отклоняет CR/LF внутри заголовков (защита от header injection).
- **Чтение из сокета.** `read_message` дочитывает заголовки, затем тело по chunked / `Content-Length` / до закрытия соединения (для ответов). У ответов 1xx, 204 и 304 тела нет.
- **Клиент.** Каждый запрос — новое соединение с `Connection: close`. Редиректы: 301/302/303 превращают POST в GET, 307/308 сохраняют метод. https — `ssl.create_default_context()` с проверкой сертификата.
- **Сервер.** HTTP/1.1 по умолчанию keep-alive, HTTP/1.0 закрывает соединение; `Connection: close` уважается. Некорректный запрос → `400`, падение обработчика → `500`, сервер продолжает работать.

## 4. Многопоточность

| Поток | Что делает | Как связан с остальными |
|---|---|---|
| Главный (Tk) | Интерфейс; единственный, кто трогает виджеты | Опрашивает очереди через `root.after` |
| `http-client` | Один запрос клиента (`RequestWorker`) | Результат → `queue.Queue[RequestResult]` |
| `http-accept` | Цикл `accept` сервера | Создаёт потоки соединений |
| `http-conn` (по одному на соединение) | Читает запросы, вызывает обработчик, пишет ответ | Лог → `HttpServer.log_queue` |

- **Остановка сервера:** выставляется `threading.Event`, закрывается слушающий сокет (`accept` имеет короткий таймаут и видит флаг), у активных соединений вызывается `shutdown`, потоки join-ятся с таймаутом. Порт освобождается, повторный запуск на том же порту работает.
- **Общее состояние:** множество соединений и список потоков защищены `threading.Lock`; очереди потокобезопасны сами по себе; глобального состояния нет — настройки и очереди передаются явно.
- **Проверка на гонки:** `python -X dev -m pytest tests/ -v` (режим разработчика включает ResourceWarning и подробные предупреждения потоков). Тесты включают 10 параллельных и 1000 последовательных запросов, остановку сервера при живых keep-alive-соединениях и проверку отсутствия утечек соединений.

## 5. Обработка ошибок

| Исключение | Когда | Где показывается |
|---|---|---|
| `ConnectionError` | отказ в соединении, неизвестный хост, обрыв, ошибка TLS, занятый порт | область ответа клиента / сообщение на вкладке «Сервер» |
| `TimeoutError` | нет ответа за заданное время | область ответа клиента |
| `ParseError` | неверный URL, мусор вместо HTTP, недопустимые заголовки | область ответа клиента; на сервере → ответ `400` |
| `HttpError(status)` | статус ≥ 400 при `raise_for_status=True` | вызывающий код |
| `ValidationError` | неверный URL, порт, таймаут, заголовки в GUI | область ответа / строка сообщения вкладки |

Кодов возврата вместо исключений нет. Все сокеты и файлы закрываются через `with`.

## 6. Логирование

Модуль `logging`: логгер `http_gui` пишет в файл `http_gui.log` и в очередь, из которой GUI показывает записи на вкладке «Настройки». Сервер дополнительно кладёт `LogEntry` в `log_queue` — из неё заполняется таблица лога на вкладке «Сервер».

## 7. Тестирование

- **Unit:** URL, парсер, сериализатор, чтение сообщений из частичного потока, роутер и обработчики, проверка ввода, форматирование и подсветка, история, логирование.
- **Интеграционные (клиент ↔ сервер):** GET/POST/статусы, 100 последовательных и 10 параллельных запросов, таймаут при «спящем» сервере, мусор вместо HTTP (400, сервер жив), keep-alive (3 запроса в одном соединении), 1000 запросов без утечек, остановка и перезапуск.
- **GUI:** `tests/test_gui_smoke.py` на настоящем Tk (пропускается без дисплея) и ручные сценарии G1–G6 из отчёта.

## 8. Линтеры

`flake8 src/ tests/ scripts/` проходит без замечаний. `pylint` запускается с `.pylintrc`; сознательно отключены (с обоснованием):

| Проверка | Почему отключена |
|---|---|
| `too-few-public-methods` | небольшие классы и dataclass без методов — осознанный выбор |
| `too-many-instance-attributes`, `too-many-arguments`, `too-many-locals`, `too-many-statements` | сервер и Tk-вкладки хранят несколько ссылок на внутренние объекты; сборка интерфейса — длинные линейные методы |
| правила имён | допустимы короткие предметные имена (`x`, `y`, `ms`) |
| для `tests/`: `redefined-outer-name`, `import-outside-toplevel`, docstring-проверки | так устроены pytest-фикстуры; в GUI-тесте `tkinter` импортируется после проверки наличия дисплея |

Точечные пометки `# pylint: disable=broad-except` стоят только там, где поток не должен умирать от неожиданной ошибки (обработчик и поток соединения на сервере, фоновый запрос клиента, обработчик логов): ошибка логируется и, где возможно, показывается пользователю.

## 9. Известные ограничения

- Только методы GET и POST в интерфейсе (клиентский код принимает любой метод).
- Без pipelining: клиент ждёт ответ, прежде чем отправить следующий запрос по тому же соединению.
- Клиент не использует keep-alive (каждый запрос — новое соединение).
- Сервер по умолчанию слушает только `127.0.0.1`.
